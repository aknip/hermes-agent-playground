ADR-002 — Freigabe der irreversiblen R1-F2-Datenmigration (two_factor), mit zwei Auflagen

Karte t_3bb0cf65 · 2026-08-18 · Feature R1-F2 „Zwei-Faktor-Authentifizierung“ · Status: gültig

Kontext

R1-F2 bringt eine Datenmigration mit: eine neue Tabelle two_factor und eine neue Spalte user.two_factor_enabled (specs/r1-f2-zwei-faktor.html, Abschnitt Datenhaltung; Migration 0043_ancient_squadron_supreme.sql). Die Migration ist additiv — sie destruiert keine Bestandsdaten, kein Spalten-Drop, kein Umschreiben bestehender Zeilen — aber sie ist trotzdem irreversibel gegen Bestandsinstallationen: Es gibt kein In-place-Downgrade, Tabelle und Spalte bleiben nach der Anwendung bestehen, sobald ein Selbst-Hoster das Update einspielt. Der Anwendungszeitpunkt ist der Boot via migrate(getDatabase(), …), kein manueller Befehl.

Kapitel 7 des Firmenvertrags (AGENTS.md) schreibt vor: Eine irreversible Änderung gegenüber Bestandsinstallationen ist immer gate-pflichtig, auch mitten im Release — und zwar unabhängig davon, ob ein Reviewer sie bemerkt. Eine Pflicht aus Kapitel 7 ist keine Beobachtung. Deshalb wurde das Irreversibel-Gate (Karte t_3bb0cf65) bereits angelegt, als das Review noch offen war, und dem CEO laut Gate-Vorlage (acht Zeilen) vorgelegt.

Optionen

Option A — Migration ohne Kopplung an den Feature-Zustand freigeben (ungehemmt)

Die Freigabe unbedingt erteilen: Die Migration ist additiv, destruiert keine Bestandsdaten, wurde vom Review auf einer echten Bestands-DB mit 79 Nutzern verifiziert, und der Aussperr-Pfad steht mit echten Spaltennamen im Repo statt nur in der Spezifikation.

Konsequenz: Das Review von R1-F2 lautet rejected — der 2FA-Challenge-Hook feuert nur auf den Passwort-Anmeldewegen (plugins/two-factor/index.mjs:222); Magic-Link, E-Mail-OTP und Social/Custom-OAuth bauen Sessions ohne zweiten Faktor (auth.ts:252–306). Das Schema würde in jeder Bestandsinstallation stehen bleiben, auch wenn das Feature in seiner heutigen Form nie sicher wird. Eine irreversible Migration für ein Feature freizugeben, das falsche Sicherheit verkauft, wäre die Reihenfolge falschherum — Schema zuerst, Sicherheit nie. Verworfen.

Option B — Freigabe mit Auflage: Migration nur als Teil eines geschlossenen 2FA (gewählt)

Die Migration wird freigegeben, aber nur als Teil eines 2FA ohne Umgehungspfad. Die Schließung der drei Anmeldewege ist Aufgabe der Nacharbeitskarte t_18e04ddf. Meldet sie strukturell_nicht_loesbar, ist die Freigabe hinfällig und 2FA wandert samt Migration nach R2 — als neue Entscheidung auf einer neuen Karte. Zusätzlich Auflage 2: der Backup-vor-Update-Hinweis wird geschrieben (nicht nur empfohlen), dort wo der Operator-SQL-Pfad steht.

Konsequenz: Die Freigabe hängt an einem verifizierbaren Zustand statt an einer Ankündigung. Scheitert die Nacharbeit, bleibt das Schema garantiert aus den Bestandsinstallationen heraus (kein Bridge-Schema zu einem nie sicheren Feature). Schlägt sie fehl, ist der Preis eine spätere neue Entscheidung — keine Fehlinvestition, weil die Migration gültig Teil von R1-F2 bleibt.

Option C — shelve: 2FA samt Migration nach R2

Die Migration gar nicht freigeben; 2FA komplett nach R2 verschieben.

Konsequenz: Bestraft die gute Datenhaltung (additiv, verifiziert, Aussperr-Pfad dokumentiert) für einen Fehler in der Anmeldung — dem anderen Karten schwerwiegender als die Datenmigration. Der Blocker liegt nicht in der Datenhaltung, sondern in der Anmeldeweg-Abdeckung, und den behebt eine andere Karte. Ein shelve würde R1-F2 verzögern, ohne das tatsächliche Risiko (Gefahr zu früher Schema-Verteilung) besser zu adressieren als Option B. Verworfen.

Entscheidung

Option B — modify: Die Migration wird am 18.08.2026 freigegeben, mit zwei verbindlichen Auflagen (CEO-Entscheid, Karte t_3bb0cf65):

  • Auflage 1: Die Migration geht NICHT vor dem geschlossenen zweiten Faktor nach main. Die Freigabe gilt für die Migration als Teil eines 2FA ohne Umgehungspfad; die Nacharbeitskarte t_18e04ddf schließt die drei Umgehungspfade. Meldet sie strukturell_nicht_loesbar, ist diese Freigabe hinfällig und 2FA wandert samt Migration nach R2 (neue Entscheidung, neue Karte).
  • Auflage 2: Der Backup-vor-Update-Hinweis wird geschrieben, nicht empfohlen — im Repo neben dem Operator-SQL-Pfad (apps/docs/core/functional/manage-your-account.mdx o.ä.), mit (a) DB-Backup vor dem Update, kein In-place-Downgrade (Tabelle und Spalte bleiben) und (b) dem Verhalten, wenn der Boot-Migrate scheitert (Betriebsausfall ohne Datenverlust, Fehlermeldungsort, Backup als Weg zurück).

Der Wortlaut beider Auflagen steht in der CEO-Antwort in der Kommentar-Sektion der Gate-Karte t_3bb0cf65 und im Gate-Vermerk von specs/r1-f2-zwei-faktor.html.

Konsequenzen

  • Die Migration ist damit freigegeben, aber nur bedingt: ohne die erfolgreiche Nacharbeit (kein strukturell_nicht_loesbar) läuft sie nicht nach main. Die Merge-Karte t_d2da004a hängt an der Nacharbeitskarte und kann dem Zustand nicht vorausgreifen.
  • Auflage 2 wird als konkreter Auftrag ausgeführt — von einer eigenen Doku-Nachfolgekarte, nicht vom Gate selbst. Bis der Hinweis geschrieben steht, bleibt der einzige Rückweg der Migration für den Selbst-Hoster unbekannt; das ist bewusst als Auflage, nicht als Befund.
  • Die Revisions-Bedingung aus Kapitel 7 bleibt: Jede künftige irreversible Änderung gegen Bestandsinstallationen ist erneut gate-pflichtig, auch wenn sie additiv ist.
  • Scheitert die Nacharbeit, gilt diese Freigabe als gegenstandslos und 2FA samt Migration wandert nach R2 — die Freigabe wird dann nicht „widerrufen“, sondern durch eine neue Entscheidung ersetzt.

Revision

Dieses ADR wird neu bewertet, wenn eines eintritt:

  • Die Nacharbeitskarte t_18e04ddf meldet strukturell_nicht_loesbar — dann ist diese Freigabe hinfällig und 2FA samt Migration wandert als neues Feature nach R2 (eigene Karte, eigene Entscheidung).
  • Ein Selbst-Hoster meldet nach dem Einspielen des Updates einen Schaden aus der Migration — dann war die Verifikation auf der 79-Nutzer-DB nicht repräsentativ und die Vorgehensweise (additive Migration, Boot-Anwendung) wird neu bewertet.
  • Die Doku-Nachfolgekarte für Auflage 2 wird nicht angelegt oder versandet — dann fehlt dem Selbst-Hoster der dokumentierte Rückweg und die Freigabe muss überprüft werden.
