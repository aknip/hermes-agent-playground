Was die Anwender jetzt können

R1-F1 · Sichtbarer globaler Sucheinstieg

Vorher: Die Suche nach einer Aufgabe, die in einem von mehreren Projekten liegt, war tastaturgebunden (Kommando-Palette mit /, eigene Such-Route) und nicht sichtbar — der größte Bruch mit dem Versprechen „find tasks across projects“. Nachher: Ein Suchfeld mit Lupen-Icon und /-Kurzbefehl steht im persistenten Header auf allen vier Seiten (Arbeitsbereichs-Übersicht, Projekt, Aufgabe, Einstellungen). Ein Klick öffnet den Such-Dialog ohne Seitenwechsel; ≥3 Zeichen finden eine Aufgabe über Projekte hinweg, ein Klick auf den Treffer navigiert ohne Reload. Die bestehenden Einstiege (Sidebar, /) bleiben intakt.

Aufwand für den Anwender: 12 Schritte für den kompletten Fluss „Aufgabe in einem anderen Projekt über den sichtbaren Header-Griff wiederfinden“ (Journey J-07, aufgabe-ueber-suche-wiederfinden.spec.ts).

Rein frontend, kein Diff unter apps/api. Beleg: Umsetzungskarte t_e4473bf4, Commit ba5eb81, Merge efb1e7c, Journey grün.

R1-F2 · Zwei-Faktor-Authentifizierung (2FA)

Vorher: Das Konto war nur durch ein Passwort geschützt; wer das Passwort hat, ist drin. Nachher: Selbst-Hoster und Nutzer können ihr Konto per TOTP (Authenticator-App, RFC 6238) absichern: In den Konto-Einstellungen unter „Sicherheit“ 2FA aktivieren, den berechneten Code verifizieren, beim nächsten Login zusätzlich den 6-stelligen Code eingeben. Opt-in — wer 2FA nicht aktiviert, loggt sich unverändert ein. Enthält die aussperr-feste Entlastung: 10 einmalige Backup-Codes beim Aktivieren, und E-Mail-OTP/Magic-Link/Social-OAuth sind für 2FA-Konten serverseitig gesperrt (verständliche Abweisung, keine stille Hintertür).

Aufwand für den Anwender: 11 Schritte für den kompletten Roundtrip „aktivieren → verifizieren → abmelden → mit 2FA anmelden → deaktivieren“ (Journey J-08, auth-haertung-2fa.spec.ts).

Was sich für Selbst-Hoster ändert

Datenmigration — JA, und sie ist irreversibel: R1 enthält Drizzle-Migration 0043_ancient_squadron_supreme. Sie legt die Tabelle two_factor und die Spalte user.two_factor_enabled an und wird beim Boot der API automatisch angewendet (migrate(getDatabase(), …)) — kein manueller Befehl.

Was das für dein Update bedeutet:

  • Vor dem Update ein DB-Backup ziehen. Es gibt kein In-place-Downgrade; Tabelle und Spalte bleiben nach Anwendung bestehen. Ein Backup ist der einzige Rückweg.
  • Wenn der Boot-Migrate-Lauf scheitert (z.B. die user-Tabelle trägt eigene, außerhalb von Drizzle gepflegte Zusätze oder einen gleichnamigen Bestand): die API startet dann nicht. Das ist ein Betriebsausfall ohne Datenverlust; die Fehlermeldung steht im API-Startlog, und der Weg zurück ist das vorgezogene Backup.

Vermerk und Operator-Pfad in apps/docs/core/functional/manage-your-account.mdx (mit Ausgabe der zwei-Spalten-Auflagen aus dem Irreversibel-Gate); Entscheidung in ADR-002; Gate-Karte t_3bb0cf65. Die Migration wurde auf einer bestehenden Installations-DB mit 79 Nutzern verifiziert.

Config: keine neuen Pflicht-Variablen. 2FA nutzt die bestehende Auth-Session; das Setup zeigt die otpauth://-URI als Text (kein QR nötig, App importiert per Text).
