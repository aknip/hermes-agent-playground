ADR-001 — Import-Architektur: CSV + WeKan

Karte t_eb272a28 · datum 2026-08-19 · Status: angenommen · Feature F-R1-1 (roadmap/q1-freigegeben.html §5)

In drei Minuten: Der Import aus CSV und WeKan wird nicht als API-Route, nicht als Erweiterung von @kaneo/planka-import gebaut, sondern als eigenständiges CLI-Paket neben dem bestehenden Importer, das denselben bewährten Schreibweg über die öffentliche Kaneo-API nutzt. Damit gibt es weder eine Schema-Änderung, noch eine Migration, noch eine Änderung der öffentlichen API-Oberfläche. Der gemeinsame Schreib-Client KaneoClient wird aus planka-import in ein geteiltes Paket extrahiert, damit kein zweiter, untypisierter Request-Layer entsteht.

1. Kontext

Es gibt bereits einen fertigen Importer: packages/planka-import (@kaneo/planka-import, bin kaneo-planka-import) mit eigenen Unit-Tests (args, colors, keys, mapping, migrate, planka, je eine .test.ts daneben). Zwei Tatsachen daran sind für diese Entscheidung maßgeblich, beide am Code verifiziert:

  • Er schreibt über die API, nicht in die Datenbank. src/kaneo.ts:22 führt eine KaneoClient-Klasse mit baseUrl und apiKey; src/kaneo.ts:139 (request()) spricht die öffentliche API über fetch mit Authorization: Bearer <apiKey> an. Alle Schreiboperationen (createProject, createTask, createLabel, createComment, …) laufen durch diesen Client (src/kaneo.ts:47–137). Ein neuer Importer nach demselben Muster braucht deshalb keine Schema-Änderung und keine Migration.
  • Die Übersetzung Fremdmodell → Kaneo ist paket-lokal und Planka-spezifisch. src/mapping.ts und src/migrate.ts enthalten die Abbildung (Spalten, Prioritäten, Termine, Labels, Kommentare, Zuweisungen). Sie ist eng an die Planka-Modelle in src/planka.ts gebunden (planka.ts:1–92). Genau diese Übersetzung muss für CSV und für WeKan jeweils neu geschrieben werden.

Die Roadmap setzt F-R1-1 „Import CSV + WeKan“ als größtes und riskantestes Stück des Quartals an den Anfang von R2, Referenzklasse feature-backend-M (roadmap/q1-freigegeben.html §5; market.html H2, Score 20). Der Feature-Schnitt umfasst fünf Karten mit einer Bau-Karte; „CSV + WeKan“ passt nicht in eine Bau-Karte, daher wird CSV vollständig gebaut und WeKan benannt auf eine Folgekarte gelegt (specs/r2-f1-import-csv-wekan.html §4).

2. Optionen

OptionWas sie kostetKonsequenz
A — Route in apps/api (Server-Import/Upload) Neuer öffentlicher Endpunkt: muss Valibot-Validierung, OpenAPI-Metadaten und den getypten Client (@kaneo/libs, AGENTS.md „keine untypenisierte HTTP-Schicht“; codebase.html §1.3, §6) mitziehen. Verlässliche Wiederaufsetzbarkeit eines halb gelaufenen Imports braucht einen Import-Status im Datenmodell → Schema-Änderung + Migration. Server-seitige Datei-Verarbeitung. Ändert genau die öffentliche API-Oberfläche, die die Spezifikation verbietet. Widerspricht dem etablierten Muster (Import läuft über die API, nicht über die DB). Schwer und riskant; Migration für Bestandsinstallationen (codebase.html §5.4).
B — Erweiterung von @kaneo/planka-import Der bestehende Importer ist als fertiges, publizierbares Paket freigegeben (package.json publishConfig.access=public, bin kaneo-planka-import). Sein Quell-Teil (src/planka.ts) und seine Mapping-Logik (src/mapping.ts) sind eng Planka-formig; der CLI-Fluss in src/index.ts liest Boards aus einer Remote-API (index.ts:69), nicht aus einer Datei. Verändert Identität und publizierte Oberfläche eines laufenden Pakets; CSV/WeKan müssten den Planka-spezifischen Arg- und Quell-Fluss teilen. Risiko für den grünen Planka-Pfad. Verworfen.
C — Zweites CLI-Paket + geteilter Schreib-Client (gewählt) Ein neues Paket @kaneo/csv-import (bin kaneo-csv-import) nach dem Planka-Muster; WeKan später als Schwester-Paket @kaneo/wekan-import. Der selbst-enthaltene KaneoClient (kaneo.ts:22, keine Intra-Paket-Abhängigkeiten) wird in ein geteiltes Paket @kaneo/kaneo-client extrahiert; planka-import importiert ihn von dort (reiner Move, Tests bleiben grün). Neue Pakete fallen unter den bestehenden packages/**-Glob in pnpm-workspace.yaml. Keine Schema-Änderung, keine Migration, keine öffentliche API-Änderung. Souveräne Trennung der Quell-/Parsing- und Mapping-Schicht je Format; kein zweiter untypisierter Request-Layer. Kosten: ein kleiner, testbewehrter Refactor im geteilten Paket.

3. Entscheidung

Option C. F-R1-1 wird als eigenständiges CLI-Paket @kaneo/csv-import gebaut, das über die öffentliche Kaneo-API schreibt (Muster aus packages/planka-import/src/kaneo.ts). Der KaneoClient und die import-domain-generischen Helfer (normalizeBaseUrl, toProjectKey/uniqueKey aus keys.ts) wandern in das geteilte Paket @kaneo/kaneo-client; planka-import wird darauf umgestellt, ohne Verhaltensänderung. WeKan kommt in einem späteren Schwester-Paket @kaneo/wekan-import (Folgekarte, siehe Spezifikation §4).

Keine API-Route, kein neues Datenmodell, keine Migration. Die öffentliche API-Oberfläche und @kaneo/libs bleiben unberührt — eine Import-Route in apps/api wäre genau die API-Änderung, die die Spezifikation ausschließt (specs/r2-f1-import-csv-wekan.html §7).

4. Konsequenzen

  • Positiv: Additive Architektur; die bestehende Import-Infrastruktur (codebase.html Modul 15) wächst um das Muster, nicht darum herum. Kein Migrations- oder Schema-Risiko für Bestandsinstallationen. Jeder Importer behält seine eigene, testbare Abbildungslogik; der geteilte Teil ist klein und beweist sich über die bestehenden Planka-Tests.
  • Kosten: Ein Refactor im bereits publizierten planka-import (Move des Clients in ein geteiltes Paket) — muss mit grünen Tests nachgewiesen werden, bevor das neue Paket darauf aufbaut. packages/** ist bereits Workspace-Glob, keine pnpm-workspace.yaml-Änderung nötig.
  • Nicht geliefert hier: WeKan-Import (Folgekarte, benannt), Attachments, Kommentar-Autor (CSV hat keine Autor-Spalte).

5. Revision

Neu bewertet wird diese Entscheidung, wenn: (a) ein Import über die API nicht mehr trägt und eine Server-Seite (Idempotenz/Status, Rechte an Projekten aus dem Kontext einer UI) den apps/api-Weg erzwingt — dann ist zuerst der Verzicht auf die öffentliche API-Änderung formal zu prüfen; oder (b) aus den drei Import-Paketen (Planka, CSV, WeKan) messbar ein vierter geteilter Baustein erwächst, der die Paketgrenze @kaneo/kaneo-client neu ziehen sollte (etwa ein gemeinsamer Abbildungs-Kern für „Board-artige“ Quell-Pakete). Ein reines Wachstum um weitere Einzelformate rechtfertigt keine Neubewertung.
